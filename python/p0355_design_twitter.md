# 355. Design Twitter · Python

[原题](https://leetcode.com/problems/design-twitter/)。

原题本地数据结构Twitter()，postTweet记录推文，getNewsFeed取自己及当前关注者最近最多10条推文，从新到旧；follow添加关系，unfollow移除关系。用户编号1..500，推文编号0..10000且每对象唯一，最多30000次外部调用；原题禁止关注自己。这里只实现内存对象，不连接任何网络服务。

_clock按发布顺序严格增加，每作者的列表按时间递增保存(clock,tweetId)。读取时收集当前关注作者及自己，每条非空作者列表只把最新候选放入最小堆，使用负时间让最新记录先弹出；弹出某作者一条后，再补入该作者的前一条。每次堆中恰有每条未耗尽来源的最新剩余项，所以反复选全局最新能得到正确前10条，不能按tweetId大小排序。

关注集合使重复follow幂等，discard使取消不存在关系不报错；查询把自己加入来源，自己的推文不依赖关注关系。关注后能读到该作者以前发布的记录，取消后整条来源不再参与。构造O(1)，发布与关注变更为均摊/期望O(1)，一次feed为O(F+10log(F+1))、临时空间O(F)，F为自己和关注者数量；heapify线性建堆。持久空间O(P+R+U)，P为推文总数，R为关系数，U为曾保存状态的用户数（上限500）。

独立模型只用全局发布列表及普通关注关系列表，按发布列表逆序筛选到10条即停，不使用按作者归并。六种发布/关注/取消变更、长度0..5共9331条序列，每步核对用户1/2/3的feed；推文ID逆序分配以区分时间顺序。最大调用对象先发布编号0..10000的10001条推文，用户1关注其余499人，再做4875轮feed/取消500/feed/重新关注，共恰30000次调用；每次feed均与参考列表核对，覆盖500用户、历史记录、边界ID及反复关系切换。
